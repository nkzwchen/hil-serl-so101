## 1. 三段式流程

```
① 录制    record_demo_so101.py   →  recordings/<时间戳>_<备注>/ep_XXXX.pkl
             每次尝试都存，**不做任何成功判断**（一段一个文件，写完即落盘）

② 标定    label_demos.py         →  recordings/<会话>/ep_XXXX.labels.json
             tkinter GUI：逐帧播放 + 局部放大，人工标"成功在第几帧"
             n/p 可跨文件，标完自动跳下一段 —— 一次能标完整个会话

③ 转换    build_demos.py         →  demo_data/so101_Ndemos_<时间戳>.pkl
             按标签置稀疏奖励、截断、只输出成功的，转成 HIL-SERL 正式 demo
```

### ③ 的两个关键点

**稀疏奖励的 off-by-one（必须处理）**
`label_demos.py` 显示的第 k 帧 = `observations[k]`。你标第 k 帧成功，说明 obs_k
就是成功状态，而**产生它的 transition 是 k−1**：
`(obs_{k-1}, a_{k-1}, obs_k, r=1, done=True)`。所以奖励落在 `k−1`，
记录截断在它之后（真跑的话 env 到那里就结束了）。**第 0 帧因此被拒绝** ——
它前面没有任何 transition 可以给奖励。

**输出前逐条对真实 space 校验**
用 `TrainConfig().get_environment(fake_env=True)` 的
`observation_space` / `action_space`，逐 key、逐 shape、逐 dtype 比对。
这是拦"形状不匹配 → 第一次 insert 就炸"那类 bug 的地方 —— 在训练**之前**拦。

**实测**：40 个 transition 逐个 `insert` 进真实的
`MemoryEfficientReplayBufferDataStore`，零报错，`sample(4)` 正常：

```
state (4,1,12) float32   cam_main (4,1,224,224,3) uint8
cam_wrist (4,1,224,224,3) uint8   actions (4,3)   rewards (4,)
```

为什么这样拆：

- **录制阶段不需要"成功判据"**。reward 现在恒 0（`TARGET_JOINT_POSE=None`），
  判据还没定 —— 录制不依赖它，就不会因为判据写错而丢掉好数据。
- **标定可以反复重做**，不用重录。
- **转换是纯确定性的**：`observations` 直接用录制时 env 输出的那一份，
  天然与 `observation_space` 一致。自己写一套录制就得手工复刻
  `INTER_AREA` resize、RGB/BGR 转换、QoS、`obs_horizon` 前导维，
  任何一处不同都会让 learner 的 ReplayBuffer 形状不匹配。

## 2. transition 格式（从官方 `record_demos.py` 核实的）

```python
dict(
    observations=obs,              # ★ 与 env.observation_space 完全一致
    actions=actions,               # ★ 4 维，[-1,1]（pan/lift/elbow/wrist_flex）
    next_observations=next_obs,
    rewards=rew,
    masks=1.0 - done,
    dones=done,
    infos=info,
)
```

整段 episode 是一个 `list[transition]`，`pkl.dump` 成文件；
learner 侧 `--demo_path` 读它，逐条 `demo_buffer.insert(transition)`，
然后 RLPD 按 **50/50** 从 demo buffer 与在线 buffer 采样。
（`single-arm-fixed-gripper` 时 `include_grasp_penalty=False`，
所以 transition 里**不需要** `grasp_penalty`。）

## 3. 录制回路（已实现：`record_demo_so101.py`）

驱动从臂的是 **`env`**（它是 follower 的唯一控制源），人通过**主臂接管**操作。
**录制阶段不做任何成功判断** —— 每次尝试原样存下，判断留给离线标定。

### 每段的 4 个阶段

```
[PRECISE]  模式A：env.reset() 把从臂放到**随机起点**（重力补偿+实测反馈+平滑斜坡）
           → 再把主臂对齐到「从臂 + 抬高偏置」，并实测确认到位
   │  c（开始录制）
   ▼
[READY]    模式A，主臂有力矩并跟住从臂。人：手离开主臂
   │  c
   ▼
[RECORD]   模式B：主臂力矩 OFF，差分基准在进入这一刻记录 → 零跳变
           人做插入；每一步都记录 transition
   │  d（人按"我插好了"）／env 自己 done（步数到上限）
   ▼
[RETURN]   ★ 仍然模式B —— 主臂**继续控制从臂**
           人用主臂把从臂带回起点附近（管子顺势拔出）
           这一段**不记录 transition**，只记元数据
   │  c（回完了）
   └──→ 回到 [PRECISE]
```

### 为什么必须有 RETURN 这一段（两个问题，一个动作解决）

1. **从臂**：episode 结束时管子插在孔里，从"插着"直接斜坡回随机起点是**大幅、突兀**的动作
2. **主臂**：差分映射下主臂**不会自己回位**，它的绝对姿态每段漂移一次插管的量。
   模拟：插管动作 `[-18°, -26°, -9°]` 时，**第 4 段主臂肘关节就撞限位**（−100°）

人的回程**同时**解决两者：从臂回到起点附近（于是 `PRECISE` 只是小幅移动），
主臂也物理地回到自己的家附近。

### 按键

| 键 | 作用 | 生效阶段 |
|---|---|---|
| `c` | 推进到下一阶段 | READY（开始录制）、RETURN（回程结束） |
| `d` | **「我插好了」→ 结束本段并保存** | RECORD |
| **`q`** | **「操作失误」→ 本次不记录、丢掉重来** | RECORD、RETURN |
| `q` | 「换个起点」（还没开始录，没有数据要丢） | READY |
| `x` | 退出整个会话（已保存的段保留；写 meta.json） | 任何 |
| `h` | 打印当前阶段可用按键 | 任何 |

**丢掉的语义**：
- **不写任何文件**，`ep` 序号**不前进** —— 下一次尝试**复用同一个序号**，
  所以 `--episodes N` 数的是"收了多少段"，而不是"尝试了多少次"
- 丢弃后**仍然进 RETURN 阶段**，所以你能把手臂安全地带回起点再开始下一次
- 会话结束时会报 `录了 N 段（共尝试 M 次，丢弃 K 次）`，`meta.json` 里也有
  `n_attempts` / `n_discarded`

> 在 RECORD 里按 `q` 与按 `d` 的区别就是"这次算不算数"。按错了也没关系：
> RETURN 阶段按 `q` 可以**切换**丢弃标记（会提示 `✖ 已标记为丢弃` / `↩ 取消丢弃标记`），
> 因为**真正落盘是在 RETURN 结束之后**。

**为什么是 `d` 而不是空格**：env 自己的空格监听在这里被 **关闭**
（`enable_keyboard=False`），因为按空格会**同时翻转接管状态**，
而 RETURN 阶段必须**继续留在模式 B**。同一个键没法既"结束录制"又"保持接管"。
接管状态由脚本按阶段显式调用 `env.set_intervening()`。

按键实现用共享模块 `so101_keys.py`（termios cbreak + select，
从 `phase1_home.py` 抽出来的 —— 原来是两份拷贝）。
它带 **`unread()` 放回语义**：自动对齐阶段只关心 `q`，按早了的 `c` 会被放回去，
不会被静默吞掉。

### ⚠️ 已接受的风险：模式 B 下松手，从臂会跟着主臂掉下去

模式 B 主臂**无力矩**。松手它就掉，而差分映射会让**从臂跟着掉同样多**
（实测主臂松手后从 +12° 一路垂到 −103°，即掉了 **115°**）。

**对策（用户决定只做这一条）**：按键盘时**用另一只手扶着主臂**。
**本脚本刻意没有**加"检测到主臂掉落就不跟从"的保护 —— 这是明确接受的风险。

### 产出

```
recordings/<时间戳>_<备注>/
    meta.json      env 参数、动作维、图像尺寸、关节名、随机化半边长、
                   **实际用的重力补偿偏置**、主臂抬高偏置、按键约定
    ep_0000.pkl    一段一个文件，写完立刻落盘（崩了不丢整场，也能边录边标）
                   {transitions:[...], meta:{n_steps, n_intervened, hz_actual,
                                            start_info, return:{...}, truncated}}
```

### 录制阶段的**质量自检**（不是成功判断）

- **接管步数占比**：0% ⇒ 忘了进模式 B，这一段没用
- **实际控制频率**：偏离目标 10Hz 太多 ⇒ 动作语义是"每步 rad"，频率变了含义就变了
- **reset 时的实际管子倾角**：> 3° ⇒ 重力补偿失配，建议重跑 `phase1_home.py`
- 回程的时长 / 关节位移

### 前置检查（任一不过就**拒绝启动**）

- 归位指令存档存在（否则管子歪 8.75°）
- **stdin 是 TTY**（否则读不到按键，一步都录不到）
- `/follower/joint_states`、`/leader/joint_states` 新鲜
- **两个相机都在出图，且不是"死图"**（连续帧完全相同 ⇒ 相机卡死，这是踩过的真实故障；
  `_get_obs` 遇到缺图是**补 0**，不检查就会静默录一堆黑图）
- 从臂力矩能打开
- 磁盘够（每段约 30MB）

实测：当前 launch 用 `use_cameras:=false` 时，前置检查**准确地拒绝启动**并指出相机问题。

## 4. 🔴 bug ①：learner 侧空壳的观测形状少了 `obs_horizon` 前导维

`ChunkingWrapper(obs_horizon=1)` 会对每个 obs 做 `v[None]`，所以真实 env 的
`observation_space` 与 `reset()` 出来的 obs 都是 `(1, ...)` 形状。
而我们自己写的 `_FakeSpacesOnlyEnv`（只给 learner 提供 spaces）漏掉了这一维：

| key | 空壳声明（改前） | actor 真实 |
|---|---|---|
| `state` | `(12,)` | `(1, 12)` |
| `cam_main` / `cam_wrist` | `(128,128,3)` | `(1, 128, 128, 3)` |

而空壳自己的 docstring 恰恰写着"必须与真实 env 完全一致，否则 ReplayBuffer
形状不匹配" —— 讽刺的是它自己就不一致。

**官方示例（`usb_pickup_insertion`）没有这个空壳**：它无论 `fake_env` 真假都套
同一串 wrapper，所以天然一致。**已按真实形状修好并实测对比确认。**

> 这个 bug 的症状会非常难查：`--learner` 启动时未必立刻炸，
> 可能要到第一次往 ReplayBuffer 里 insert 才报形状错。

## 5. 🔴 bug ②：模式 B 用"主臂绝对角"，会抹掉随机化并毁掉 transition 自洽性

原先 `step()` 模式 B 写的是：

```python
target5 = leader[:5] - LEADER_HOME_OFFSET        # ← 绝对映射
```

两个后果，都会**静默毁掉数据**：

**① `reset()` 的随机化被当场抹掉。** 从臂刚被随机化到某个起点，人手一接管，
从臂立刻跳回主臂所在的姿态。实测：两臂相差 7.6° 时，旧写法在接管瞬间
产生 **3.44° 的跳变**（新写法 0.00°）。

**② 录下来的 action 与从臂实际位移不自洽。** `intervene_action` 是
"主臂位移 / scale"，而 env 实际下发的是主臂的**绝对角** —— 两者不是一回事。
RLPD 的 transition 要求 `(obs, action, next_obs)` 满足"在 obs 施加 action 得到
next_obs"，绝对映射下这个等式不成立：

```
主臂移动 3°  →  action×scale 要求从臂位移 [0, 1, 1, 1, 0]°
              绝对映射实际位移      [0, −3.44, 2.58, −1.15, 0]°   ❌ 完全不同
```

**改成差分映射**（与 `phase3_cartesian_teleop.py` 同款）：

```python
target5 = 接管瞬间的从臂位置 + (主臂当前位置 − 接管瞬间的主臂位置)
```

- 接管瞬间零跳变 ✓
- 从臂位移 == 主臂位移 == `action × action_scale` ✓ 自洽
- 主臂的"家偏置"（抬高 2.5cm）在 `主臂当前位置 − 主臂基准` 里**自动抵消**，
  不再需要显式减 `LEADER_HOME_OFFSET`

基准在 `_enter_mode('human')` 时记录；回到 policy 时清空。

## 5.5 🔴 bug ③：两个工具各写了一遍"读录制文件"，然后读岔了

`label_demos.py` 支持 **4 种**录制文件布局，`build_demos.py` 只认 **1 种**
（`{'transitions': [...]}`）—— 因为格式分发在两个文件里各写了一遍。
后果：`make_dummy_recording.py` 造的多段文件（`{'episodes': [...]}`）能标定，
一到 `build_demos.py` 就 `KeyError: 'transitions'`。

**修法**：读盘抽成 `so101_recording_io.py`，两边共用：

| 函数 | 作用 |
|---|---|
| `load_raw(path)` | 格式分发 → `(每段的原始 transition 列表, meta)`；**唯一的格式真相源** |
| `labels_path(rec)` | `ep_0000.pkl` → `ep_0000.labels.json` |
| `load_labels(rec)` | → `{段号: {'status':..., 'frame':...}}` |

`label_demos.py` 只负责把原始 transition 转成要渲染的帧；`build_demos.py` 直接用原始
transition。顺带 `build_demos.py` 现在**逐段取标签**（以前只读第一段），多段文件里
不同段的成功帧不再互相覆盖。

### 同类隐患：键位表与 `start_info` 的"静默变 0"

| 契约 | 单一来源 | 谁在核对 |
|---|---|---|
| 录制按键语义（写进 `meta.json`） | `record_demo_so101.KEYMAP` | `test_record_flow.py` 直接断言它 |
| `env.reset()` 的 `start_info` 必含键 | `record_demo_so101.START_INFO_KEYS` | 录制器首次 reset 后硬查；`test_env_reset.py` 拿**真机**数据核对 |

两处都曾经是"两个文件各抄一份"：

- 键位表改过之后，录制器正常、`test_record_flow.py` 却拿旧键位断言，白白报错。
- `start_info` 的键从 `a_m/b_m` 改成 `dx_m/dy_m/dz_m` 时漏改录制器 —— 而录制器
  全程用 `.get(..., 0)` 读，**键名写错不会报错，只会把元数据静默写成 `0.00cm`**。
  所以现在录制器在第一次 `reset()` 后就硬查这张表，缺键直接抛错。

## 6. 标定工具 `label_demos.py`

tkinter GUI，**必须用 `DISPLAY=:0`**（本机 X 只走 unix socket；
`127.0.0.1:0.0` 连不上 —— 当初 pynput 判定"连不上 X"大概就是这个原因）。
conda 的 OpenCV 是 `GUI: NONE` 构建，`cv2.imshow` 不可用，所以用 tkinter。

界面：左边 `cam_main`、中间 `cam_wrist`（各 300×300），右边放大镜（460×460）。
放大镜的取景框会画在两个视角上，一眼能看出在看哪儿。

| 按键 | 作用 |
|---|---|
| `←` / `→` | 逐帧 ∓1 |
| `Shift+←` / `Shift+→` | ∓10 帧 |
| `Home` / `End` | 首帧 / 末帧 |
| 空格 | 播放 / 暂停（10fps，与 `ENV_HZ` 一致） |
| **`s`** | **把成功标在当前帧**，并自动跳到下一段 |
| **`f`** | **本段标失败**，并自动跳到下一段 |
| `c` | 清除本段标记 |
| `n` / `p` | 下一段 / 上一段 |
| `z` / `Z` | 缩小 / 放大（1~16，显示**实际**屏幕倍数） |
| `r` | 放大镜回到画面中心 |
| `t` | 切换放大来源（主视角 / 腕部） |
| `g` | 最近邻 / 双线性插值 |
| 鼠标点击/拖动 | 把放大镜移到该处 |
| `w` / `q` | 保存标签 / 退出（标过才自动保存；一段都没标就不写文件） |

**每个操作都还有对应的按钮**（首帧 / ±1 / ±10 / 播放暂停 / 末帧 / 标成功 / 标失败 /
清除 / 上下一段 / 保存）。为什么必须有按钮：按键能不能送到窗口取决于
焦点和窗口管理器，光靠键盘会出现"按了没反应"；启动时还会 `focus_force()` 抢一次焦点。

标签写到 `<录制文件>.labels.json`，与录制数据**分开存**，所以标定可以反复重做。

### 观测分辨率：128 → **224**（2026-09-29 改）

**原来 128 是错的。** 相机源分辨率是 `cam_main` **640×480**、`cam_wrist` **424×240**，
缩到 128 会把细节全丢掉 —— 标定时**看不出试管有没有进孔**，
而**策略看到的是同一张图，它也没法学**。这不是工具问题，是任务可见性问题。

改动只有一个旋钮：`config.py` 的 `IMAGE_SIZE = 224`（`env.py` 与 learner 空壳都从它取）。

**约束重新评估**（前提：**训练在云端，本地只做推理**）：

| 项 | 128 | 224 | 说明 |
|---|---|---|---|
| 本地推理 | ~1.5ms | **~2–3ms** | 实测 CPU 约 **1 TFLOPS**（matmul），ResNet-10×2 相机在 224 约 1.9 GFLOP；**完全可忽略** |
| 本地磁盘 / 上传 | 10MB/段 | **30MB/段** | 50 段 ≈ 1.5GB |
| actor 排队缓冲 | 0.5GB | 1.5GB | `QueuedDataStore(50000)` 是**上限**；云端 learner 持续取走，实际很小 |
| 云端训练 | — | 图像大 3 倍 | GPU 上无压力 |

**为什么选 224 而不是 256 / 320**：

- `cam_wrist` 纵向只有 **240**，再大就是**插值放大（假分辨率）**
- 224 是 **32 的整数倍**，正好是 ResNet 的下采样步长（特征图 7×7 干净）
- 224 也是 ImageNet 预训练 ResNet 的标准输入尺度

> `cam_main`（640×480）其实还能给更高。将来若要**分相机**设置，
> 改 `IMAGE_SIZE` 为 dict + `env.py` 的 `observation_space`（它本来就是逐 key 建的 Box）。

### ⚠️ 遗留风险：actor 本地的排队缓冲没有硬上限

`train_rlpd.py` 里 actor 用的是 `QueuedDataStore(50000)` —— 队列上限 5 万条。
**云端 learner 持续取走时它几乎是空的**，但如果 learner 长时间卡住 / 断线，
队列会一路涨：224 时 50000 × ~300KB ≈ **15GB** → 本地 7GB 内存直接 OOM。

建议把它调小（例如 2000~5000，一行改动），作为本地内存的硬上限。
本次**没有擅自改**，因为它同时是"learner 跟不上时会不会丢数据"的取舍。

### ⚠️ 放大镜的真实能力边界

放大镜把**已有的源像素**放大（1~16×，最近邻/双线性可切），它**不能恢复分辨率**。
所以：如果连 224×224 都看不出插没插进去，那说明**腕部相机该怼得更近**，
而不是继续加分辨率 —— 因为策略看到的也是同一张 224 的图。

放大镜的取景/点击换算按**实际图像边长**自适应（`_src_dim()`），
不写死 128 —— 分辨率一改，ROI 框和点击位置都跟着对。
