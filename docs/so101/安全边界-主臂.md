## 0. ⚠️ 重要更新（2026-09-28）：真的把主臂舵机顶到过热了

**这份文档记录的边界，在真实运行中触发了舵机过热保护。**
而且**过热的是 `elbow_flex`，不是 §3 推测的 `shoulder_lift`**。

### 事故日志（原文）

```
[leader_ros2_node-6] [ERROR] Failed to set leader torque:
    RuntimeError: Failed to write 'Torque_Enable' on id_=3 with '1' after 1 tries.
    [RxPacketError] Overheat error!
```

`id=3` 经标定文件确认 = **`elbow_flex`**
（leader 的 id 映射：1=shoulder_pan, 2=shoulder_lift, 3=elbow_flex,
4=wrist_flex, 5=wrist_roll, 6=gripper）。

### 时间线（证明是热保护，且会自行恢复）

```
1790600543  失败  Overheat error, id=3
1790600562  失败  Overheat error, id=3
1790600618  成功  Leader torque -> ON     ← 约 75 秒后冷却自愈
```

### 根因链

```
① 主臂 elbow_flex 被顶住（撞桌 / 顶在限位上）
        ↓
② 归位的【迭代修正】发现"到不了位"，持续加大该关节的指令偏移
   （日志里偏移一路涨到 10.21°、13.03° …）
        ↓
③ 舵机堵转 → 电流大 → 发热
        ↓
④ 触发【过热保护】→ Torque_Enable 写入被直接拒绝
        ↓
⑤ 力矩打不开 → 该关节使不上力 → 归位误差涨到 34.7° → 中止
```

**这正是本文档 §4.3 提前警告过的风险（软件积分的饱和行为）真实发生了。**
当时只记录、没实现防护 —— 现在已在 `phase1_home.py` 里补上（见 §8）。

### 结论修正

| 项 | 原判断（§3）| **修正后** |
|---|---|---|
| 瓶颈关节 | 推测 `shoulder_lift`（离 URDF 上限最近）| **实测是 `elbow_flex`** |
| 边界形状 | 可能是一个关节的常量上限 | **显然不是**，至少涉及 `elbow_flex` |
| 可用性 | 单点记录 | **单点不足以定义边界（§6 已预警，现被证实）** |

### 应急处置

**如果主臂力矩打不开、报 `Overheat error`：**
1. **停止驱动该臂，等它冷却**（实测约 1~2 分钟自行恢复）
2. 急用可加 `--no-leader`，只归位从臂
3. 不要反复重试（会持续发热）

## 1. 背景：为什么会有这份文档

在 Phase 1「双臂归位」的压力测试中（目标 = `START_JOINT_POSE + [0°, +55°, −65°, 0°, 0°]`），
出现了一个现象：

- **follower 正常到位**（最终误差 0.09°~0.23°）
- **leader 明显到不了位**（残差停在 2.5~2.8°，而且迭代修正把指令偏移一路推到 10.21°）

使用者确认：**主臂在那个方向被桌子挡住了** —— 是真机的物理干涉，不是控制问题。

于是把**主臂当时停在的位置**记录下来，作为一条**安全边界**：
以后再往这个方向驱动主臂时，不应该越过它。

## 3. 怎么解读：瓶颈是 `shoulder_lift`

关键对比：

```
                    距 URDF 上限余量
shoulder_lift            +0.4822 rad   ← 27.6°，最紧
gripper                  +0.4937 rad
shoulder_pan             +1.5663 rad
wrist_flex               +1.9948 rad
elbow_flex               +2.7249 rad
wrist_roll               +2.7758 rad
```

`shoulder_lift` 是**机械行程上最接近上限**的关节，同时它也是**几何上最先把臂抬到桌面上方**的关节。
所以这条边界**大概率等价于一个 `shoulder_lift` 的软上限**：

```
shoulder_lift  ≲  +1.2628 rad  (≈ +72.35°)
```

**但这只是最可能的解读，不是已证实的结论** —— 见第 6 节的待确认项。

## 4. 建议怎么用（尚未实现）

### 4.1 在下发主臂指令前做软限幅

主臂的指令路径是 `/leader/arm_command`（`Float64MultiArray`，6 个弧度值）。
驱动主臂的地方目前有两处：

| 位置 | 用途 |
|---|---|
| `phase1_home.py` → `pub_leader()` | 归位时驱动主臂 |
| `SO101Env._drive_leader()`（env.py） | 模式 A 下让主臂跟随从臂 |

**建议**：在这两处下发前，把 `shoulder_lift` 夹到 `≤ 1.2628 rad`。

### 4.2 与 leader 桥已有的硬限幅配合

`LeaderBridge` 已有 `max_relative_target = 20.0`（度/步，以"上一条命令"为基准），
那是**速率**限制；本文件记录的是**位置**边界。两者是互补的，不冲突。

### 4.3 与迭代修正的相互作用（值得注意）

Phase 1 的迭代修正会对"到不了位"的关节持续加大指令偏移。
主臂被挡住时，偏移被一路推到 **10.21°**（上限 `CORRECTION_MAX = 20°` 兜住了）。

**这是软件积分的饱和行为**：被挡住的关节会被持续施加越来越大的推力。
虽然被 20° 上限卡住、不会无限增长，但**会持续对抗**。若以后要在"可能被挡住"的场景下
使用迭代修正，应加一条规则：**残差长时间不下降就放弃对该关节的修正**。

## 6. 待确认 / 如何细化

一条**单点记录不足以定义完整的安全边界**。要让它真正可用，需要补三件事：

1. **确认受限方向** —— 是"`shoulder_lift` 向上越不过"？还是"某几个关节的某个组合位形下会碰桌"？
   - 验证方法：固定其它关节，只把 `shoulder_lift` 往正方向一点点加，看它在哪个值被挡住
2. **确认边界形状** —— 是一个关节的常量上限，还是随其它关节角度变化的曲面？
   - 若是曲面，单点记录就不够，需要扫几个位形
3. **确认是可重复的干涉**（每次都在同一角度停住），还是偶发
   - 从两次压力测试看，leader 都在 `shoulder_lift ≈ 1.26` 附近停住，**看起来是可重复的**

## 9. 主臂归位抬高偏置（2026-09-29）

### 9.1 需求与依据

现场：**主臂那张桌子比从臂这边略高**。主臂若按"和从臂一模一样的关节角"归位，
夹爪就离它自己的桌面太近 —— 正是 §0 里 `elbow_flex` 被顶住过热的那条路径。
对策：**只给主臂**的归位目标加一个抬高偏置，从臂目标一个数都不动。

选 `shoulder_lift` 而不是 `elbow_flex`（起点处用 `so101_kin` 正运动学实测）：

| 偏置关节 | 每 −10° 抬高 | 水平位移 | 备注 |
|---|---|---|---|
| `shoulder_lift` | **+5.9cm** | 仅 2mm | ✅ 采用：抬得最多、几乎纯竖直 |
| `elbow_flex` | +4.9cm | 14mm | 会把夹爪往旁边带 |

主臂只是**人手握的把手**，"管子竖直"只对从臂插管有意义，所以主臂可以随便改姿态。

**默认 2.5cm**（`--leader-lift`，填 0 关闭）。换算不是写死系数，而是用正运动学
**二分求解**，并当场把结果验回来：

| 抬高 | `shoulder_lift` 偏置 | `shoulder_lift` 目标 | 夹爪高度 |
|---|---|---|---|
| 0（两臂同姿态） | 0.00° | +16.26° | 16.1cm |
| **2.5cm ← 当前默认** | **−4.18°** | **+12.09°** | **18.6cm** |
| 5cm（2026-09-29 曾用） | −8.41° | +7.85° | 21.1cm |

> 起初按 5cm 做出来真机实测通过（主臂比从臂高 +4.8cm），但使用后觉得**抬多了**，
> 同日改成 2.5cm。改的只是一个常量 `LEADER_LIFT_DEFAULT_CM`，
> `phase1_home.py` / `env.py` 都从这里取，不需要改第二处。

### 9.2 ★ 真正的坑：绝对语义 vs 差分语义

加上偏置后，**两臂的家姿态不再相同**。而原先有三处代码默认"两臂归到同一点"，
于是会把偏置当成"人工输入"，从臂会莫名其妙地被抬走：

| 位置 | 原写法 | 后果 | 已改为 |
|---|---|---|---|
| `phase3_cartesian_teleop.py` direct 模式 | 1 秒内把软启动权重从 1 **衰减到 0**（= 从臂直接用主臂**绝对角**） | 从臂进遥控时被抬 8.41°，离开 Phase 0 已验证的插管起点 | 以"进入时的实测差"为**永久基准**的差分映射，从臂只跟随主臂的**变化量** |
| `env.py` 模式 A（主臂跟随从臂） | 把从臂位置**原样**发给主臂 | 主臂被拽到从臂姿态 → 贴住自己更高的桌面 → 过热 | 发 `从臂位置 + 偏置` |
| `env.py` 模式 B（从臂跟随主臂） | 从臂目标 = 主臂**绝对角** | 从臂被抬高一个偏置 | 从臂目标 = `主臂位置 − 偏置` |

**统一约定**（已写进 `so101_home_pose.py` 的 docstring）：

```
follower_pose  =  leader_pose  −  LEADER_HOME_OFFSET
```

偏置为 0 时全式退化成"两臂同姿态"，与旧代码完全等价（已回归验证）。

### 9.3 单一真相源

姿态 / 限位 / 偏置只在 **`hil-serl/examples/experiments/so101/so101_home_pose.py`**
定义一次，`phase1_home.py`、`phase3_cartesian_teleop.py`、`env.py` 一律 import。
新增任何"读两臂姿态"的代码，都必须先想清楚它是**绝对**语义还是**差分**语义 ——
这是这一节存在的唯一理由。

### 9.4 验证记录

- 换算精度：请求 +1/+2/+3/+5/+8/+10/+15/+20/+25/+30cm，误差均 **< 0.005cm**
- 只动 `shoulder_lift`：非零分量下标 = `[1]` ✅
- 全量程单调性：二分区间内 `shoulder_lift` 减小 → 高度**严格单调上升** ✅
- 限位：+30cm → `shoulder_lift −57.96°`，在 `[−100°, +100°]` 内 ✅
- 映射零跳变：`phase3` 下发 − 从臂原位 = `[0,0,0,0]`；`env.py` 模式 B 同理 ✅
- `env.py` 模式 A 下发仍是**正好 6 个数**（`/leader/arm_command` 的硬要求）✅
- `--leader-lift 0` 回归：输出与加偏置前**逐字一致** ✅



## 10. 🔴 事故：开力矩瞬间"跳起来又回去"（2026-09-29）

这是**第一次带着抬高偏置真正驱动主臂**时发生的，但它跟抬高偏置**无关** ——
是一个一直潜伏在 bridge 里的坑，只是以前没被触发得这么明显。

### 10.1 现场

```
python phase1_home.py
  /leader/set_torque -> ON  ✅
❌ leader 跟随误差过大（34.8°）—— 可能有人按住主臂或被挡住，已中止。
  leader   最终误差 = 104.862°   （未跑到修正轮）
```

使用者描述：**"主臂突然跳起来，又回去了"**。

### 10.2 根因：`Torque_Enable=1` 会冲向旧的 `Goal_Position`

Feetech 舵机的行为：`Torque_Enable` 置 1 的瞬间，舵机会**立刻冲向自己
`Goal_Position` 寄存器里的值**。而这个寄存器在力矩关闭期间**不会被更新**。

而 lerobot 的 `enable_torque()` 只做两件事：

```python
for motor in ...:
    self.write("Torque_Enable", motor, TorqueMode.ENABLED.value)
    self.write("Lock", motor, 1)
```

**完全不碰 `Goal_Position`**（已读源码确认）。于是：

| 时刻 | 发生了什么 |
|---|---|
| 上一次运行结束时 | `Goal_Position` 里留下的是**抬高后的目标** |
| 本次 `home()` 读 `l0` | 读到的却是**下垂**的实测位置（力矩关着，手臂压在桌上） |
| `set_torque(True)` | 舵机立刻冲向旧目标 → **"突然跳起来"** |
| `time.sleep(0.3)` 期间 | 已经爬升了约 35° |
| 循环第一帧 | 下发的是 `l0`（下垂位置）→ 把它**拽回去** → **"又回去了"** |
| 误差检查 | `\|实测 − 插值参考\|` = **34.84°** > 阈值 34° → 第一帧就中止 |
| 中止后 | 停在"下垂指令"上 → 最终误差 104.86° ≈ 起点 |

### 10.3 为什么之前查不出来：日志里什么都没有

同期 bridge 日志**一条 ERROR 都没有**（既无写失败，也无过热），因为**舵机根本没出错**。
它只是老老实实执行了"冲向目标寄存器"这个指令。

更糟的是，`LeaderBridge.command_callback` 里有一段**重复粘贴的 `try/except`
合并残留**：第一个 `except` 里又调了一次 `sync_write`，第二个 `except`（负责打印
限流日志的那个）永远不可达。于是**即使真的写失败，也不会打日志** ——
这直接让我第一次排查时误判成"没有写失败"。

### 10.4 定位过程中的关键数字

这一步值得记下来，因为它是"证据"而不是"猜测"：

- `max_l_per = 34.84°` **不是** 111°（初始需移动量）→ 说明中止发生在**很早期**
- `最终误差 = 104.86°`，而初始需移动 111.06° → 主臂**净移动只有 6.2°**，
  即"跑完又回到起点附近"

这两条只有"开局先被弹出去、再被指令拽回来、然后中止"能同时解释。

### 10.5 修复

**改在 bridge 基类**（`SO101ROS2Bridge._sync_goal_to_present()`），
开力矩**之前**先：

1. `sync_read('Present_Position')` 读当前实测位置
2. `sync_write('Goal_Position', 当前实测位置)` —— 让目标寄存器不再是旧值
3. 把限幅基准 `_last_cmd` 也重置为实测位置
   （它同样是跨次运行残留的，会把第一条命令限幅到错误位置）
4. **然后**才 `enable_torque()`

> ⚠️ 踩到的第二个坑：`FollowerBridge` 和 `LeaderBridge` 是**兄弟类**
> （都继承 `SO101ROS2Bridge`），不是父子关系。方法放子类里，另一边根本继承不到。
> 所以这个 helper 必须放在**基类**。

修的时候顺手把从臂那侧也改了 —— 它的 docstring **早就写明**了这个隐患
（"恢复 True 时会瞬间重新跟随当前命令位置，可能有跳变"），只是一直没修。

**影响面不止归位脚本**：`env.py` 每次"人类接管 ↔ 回到 policy"切换都会开/关主臂
力矩，同一个坑会在**每次接管结束时重演**。

### 10.7 第一版修复**自己引入的第二个 bug**（同日发现）

第一版的 `_sync_goal_to_present()` 是**无条件**执行的。这在"舵机本来松着"时是对的，
但"舵机**已经带力矩**"时就错了：

> 本舵机是比例位置环且 `I_Coefficient = 0`，它正是靠**"指令值比实际位置高出一个
> 静差量"**来顶住重力的。把 `Goal_Position` 抹成当前实测位置 = **撤掉顶重力的力**
> → 机械臂立刻下垂。

现场：主臂开力矩后**下垂 4.0°**，触发了我刚加的保险并中止。

**正确做法：只对当前确实无力矩的电机做同步。** `Torque_Enable` 是可读寄存器
（地址 40，长度 1），所以能拿到权威状态：

```
off = sync_read('Torque_Enable') 中值为 0 的电机
if off:                      → 只同步这些电机
elif 全部有力矩:              → 跳过（避免抹掉重力偏置）
if 读不到:                    → 保守地照旧同步全部
```

两害相权：该同步却没同步 → 松着的臂猛冲旧目标（十几度，危险）；
不该同步却同步了 → 有力矩的臂下垂几度（难受，但不危险）。所以读不到时选择"同步"。

### 10.8 教训：只测一半会以为修好了

`test_torque_jump.py` 因此改成**两个阶段都测**：

| 阶段 | 情形 | 做错了会怎样 |
|---|---|---|
| A | 舵机**松着** → 开力矩 | 不写 `Goal_Position` → 冲向上次运行留下的旧目标 → **向上猛跳** |
| B | 舵机**已带力矩** → 再开一次 | 无条件抹平 `Goal_Position` → 抹掉顶重力的静差偏置 → **向下垂几度** |

只测 A 会以为修好了，其实引入了 B。B 正是第一版修复引入的。实测两个阶段现在都是 **0.00°**：

```
✅ 阶段 A 松着→开         最大偏移 =   0.00°
✅ 阶段 B 带力矩→再开       最大偏移 =   0.00°
```

bridge 日志也确认两条分支都走对了：

```
leader Goal_Position 已同步为当前实测位置：['elbow_flex', 'gripper', ...]   ← 阶段 A
Leader torque -> ON
leader 已全部带力矩，跳过 Goal_Position 同步（避免抹掉重力偏置）           ← 阶段 B
Leader torque -> ON
```

### 10.9 新增的保险（`phase1_home.py`）

开力矩后**重新读一次主臂位置**并用它当轨迹起点，且移动 > 3° 就**立即中止**。
中止时打印逐关节位移与方向，并据此提示是机制①（向上猛跳）还是机制②（向下垂），
避免把两种成因混为一谈 —— 第一版只写了"bridge 没重编"，在机制②上就是**误报**。

### 10.10 ⚠️ 更正：没有"保持力矩时会缓慢漂移"这回事

排查过程中我曾推测"主臂在保持力矩时会缓慢漂移约 2.6°（比例环无积分项 + 静摩擦）"。
**这个推测是错的**，实测推翻了它：归位完成后连续 60s 采样，两臂漂移均为 **0.00°**。

那 2.6° 是一次性位移（很可能被人手碰过），不是持续漂移。记录下来是为了以后
不要拿一个没验证过的解释当结论。

### 10.11 ⚠️ 遗留问题：抬高 2.5cm 是"指令量"，不是"实测高度差"

默认改成 2.5cm 后实测（`shoulder_lift` 目标：从臂 +16.26°、主臂 +12.09°）：

| | 从臂 | 主臂 |
|---|---|---|
| `shoulder_lift` 实测 | +15.74°（差 0.53°） | +13.10°（差 1.01°） |
| `elbow_flex` 实测 | +2.86°（**差 2.11°**） | +5.32°（差 0.35°） |
| 夹爪高度 | 17.5cm | 17.8cm |

**指令/运动学上主臂比从臂高 2.5cm（18.6 vs 16.1cm），但实测只高 0.3cm。**
原因不是主臂没抬，而是**两臂的下垂量不一样**：

- 从臂 `elbow_flex` 比主臂多垂 **2.5°**（它夹着试管，负载更大），
  而"肘关节更低 → 夹爪更高"→ 把主臂抬的那部分**抵消掉**
- 从臂夹爪比自己的名义高度**高出 1.4cm**；主臂比自己的名义高度**低 0.8cm**
- 2.5 − 1.4 − 0.8 ≈ 0.3cm ✓

所以：
- 若目的是"让主臂离开它自己的桌面 2.5cm" → **已达成**（这正是 `--leader-lift` 的定义）
- 若目的是"让主臂**实测**比从臂高 2.5cm" → 需要把偏置加大到约 4.7cm
  （粗略线性外推，**需实测确认**：加大偏置会同时改变主臂自身的下垂量），
  **或者**根治从臂肘关节那 2.11° 的残余下垂

**从臂肘关节残差 2.11° 值得单独查**：迭代修正的收敛日志明明写着"第 2 轮后
follower 0.15°"，但最终肘关节却是 2.02° —— 说明**第 3 轮修正把它弄差了约 2°**
（而第 3 轮的指令偏移只从 4.22° 变到 4.31°）。这个小变化引起 2° 的响应，不合理，
怀疑与"卡住保护"逐关节清零残差的交互有关。
