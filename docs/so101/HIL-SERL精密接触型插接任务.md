## 1. 概述

### 1.1 什么是 HIL SERL

HIL SERL 是一种人类在环的真机强化学习框架，核心特点：

- **分布式 Actor-Learner 架构**：Actor 进程在机器人端实时执行策略并采集数据，Learner 进程在本地 RTX 4090 主机上异步更新策略权重，两者通过 Replay Buffer 和参数广播松耦合协作。
- **人类在环干预**：训练过程中操作者可随时通过游戏手柄 / SpaceMouse / 键盘介入，修正危险或无效行为，保障硬件安全并加速收敛。
- **安全机制**：关节限位、末端执行器（EE）限位、感兴趣区域（ROI）裁剪、WandB 实时监控。

论文：<https://hil-serl.github.io/static/hil-serl-paper.pdf>
代码：<https://github.com/rail-berkeley/hil-serl>

### 1.2 项目实战背景：松灵机械臂 USB 插拔任务

本指南基于在松灵机械臂上搭建的真机 USB 插拔任务整理，系统核心组成：

- **策略观测**：多路 RealSense 图像（两个腕部视角 + 一个第三视角）+ 机械臂本体状态（关节等 proprio 信息）。
- **动作空间**：末端相对控制，输出归一化的末端平移增量，结合任务约束锁定末端姿态。
- **人工干预**：接入 SpaceMouse 作为人工干预通道，策略即将失败或机械臂进入不期望区域时，实时替换策略动作并把干预数据回流到训练中。
- **奖励信号**：用第三视角相机采集成功和失败样本，训练二分类 reward classifier，自动判断任务是否完成。
- **工程架构**：机械臂 SDK 封装到 ROS2 控制节点中，通过 Flask HTTP bridge 向上层强化学习环境暴露 `getstate`、`pose`、`jointreset`、夹爪控制等接口，打通真机控制、视觉观测、人工干预和在线训练链路。

### 1.3 RL 基础概念速查

HIL SERL 基于 SAC（最大熵 Actor-Critic）框架，项目中实际使用的是 **RLPD（Offline-to-Online）** 算法。常用算法分类：

| 算法 | 数据范式 | 策略关系 |
|---|---|---|
| PPO | Online | On-policy |
| SAC | Online | Off-policy |
| TD3 | Online | Off-policy |
| IQL | Offline | — |
| RLPD | Offline-to-Online | Off-policy |
| DPO | Offline Preference | — |

> **重点掌握**：PPO、SAC、RLPD。SAC 是 off-policy 最大熵 Actor-Critic，通过最大化累计奖励 + 策略熵来鼓励探索；PPO 是 on-policy，通过 clipped objective 限制更新幅度，训练更稳但样本效率低。

### 1.4 典型应用场景

- 机械臂抓取与放置（Pick & Place）
- 轴孔装配 / USB 插拔（Peg Insertion）
- 线缆布线（Cable Routing）
- PCB 元器件插装
- 其他样本采集成本高、硬件安全要求高的操作任务

### 2.3 数据流与调用链路

下图展示了从机械臂底层 SDK 到上层算法层的完整数据流和调用关系（原 ASCII 图右侧截断，按可见部分转录）：

```text
┌─────────────────────────────────────────────┐
│                上层算法层                     │
│  ┌──────────────────┐        ┌────────────  │
│  │ RLPD / SAC       │◄──────►│ Repl……       │
│  │ Actor+Critic     │───────►│ (prio……      │
│  └──────────────────┘        └────────────  │
│                                             │
│         │ 参数广播（下行）      │ t……        │
│         ▼                     │             │
┌─────────────────────────────────────────────┐
│            Flask HTTP……                     │
│  POST /action            GET /get……        │
│  （下发动作指令）        （获取观测数……）     │
└─────────────────────────────────────────────┘
│                                             │
│                    ▼             ▲          │
┌─────────────────────────────────────────────┐
│              ROS2 控……                      │
│  ┌────────────────┐        ┌──────────      │
│  │ 动作订阅节点    │───────►│ 机……           │
│  │ /action_cmd    │        │ （松灵……       │
│  └────────────────┘        │ (MIT)……       │
└─────────────────────────────────────────────┘
```

**调用链路说明：**

1. **算法层 → HTTP Bridge**：Learner 中的 Actor 网络推理出动作，通过 `POST /action` 下发到 Flask 服务。
2. **HTTP Bridge → ROS2**：Flask 收到动作后，发布到 ROS2 话题 `/action_cmd`。
3. **ROS2 → 机械臂 SDK**：ROS2 控制节点订阅动作指令，调用松灵臂 SDK 执行 MIT 混合控制。
4. **机械臂 → ROS2**：SDK 回传关节状态、末端位姿，相机节点发布图像。
5. **ROS2 → HTTP Bridge**：Flask 通过 `GET /getstate` 聚合图像和 proprio 数据返回给算法层。
6. **Actor端 → Reward Classifier**：第三视角图像在 Actor 端直接送入 ResNet 二分类器，推理出 reward（成功=1，失败=0）。Classifier 不跨网络运行，也不直接写 Buffer。
7. **transition 构建 & 上传**：Actor 端将 (obs, action, reward, next_obs, done) 打包为完整 transition，通过网络上传到 Learner 端的 Replay Buffer。
8. **Learner 更新**：从 Replay Buffer 采样训练 Actor 和 Critic，定期将新参数广播给 Actor。

## 3. 真机部署流程

### 3.0 流程总览

> **安全前置**：真机训练全程必须有人在场，手不离开急停按钮；训练初期机械臂动作随机且剧烈，必须限速、限工作空间；SpaceMouse 是最后一道安全防线，随时准备接管。

整个部署流程分为 **9 个阶段**，可分为"一次性准备"和"每次训练必做"两类：

| 阶段 | 做什么 |
|---|---|
| 3.1 环境搭建 | 安装系统依赖、Python 环境、ROS2 控制节点、Flask HTTP 接服务 |
| 3.2 机器人配置 | 连接机械臂、配置控制模式、置安全限位与初始化位姿 |
| 3.3 相机与感知 | 安装多路相机、定义观测空间（图像 + 本体状态） |
| 3.4 动作空间定义 | 确定动作形式（末端相对控制）、锁定姿态、固定夹爪 |
| 3.5 Reward Classifier 训练 | 采集成功/失败图像数据、训练分类奖励器、在线推理给奖励 |
| 3.6 RL 算法配置 | 选择算法（RLPD）、配置双 Buffer、设置超参数 |
| 3.7 人工干预准备 | 配置 SpaceMouse、理解硬替换机制、明确干预时机 |
| 3.8 启动训练 | 同时启动 Actor（机器人端）和 Learner（GPU 端），确认数据通 |
| 3.9 评估与部署 | 评估成功率、导出模型、真机推理部署 |

> **数据主线**：整个流程以数据为核心——相机图像 → 人工标注成功/失败 → 训练 Reward Classifier → 在线推理生成 reward → transition 存入 Replay Buffer → 混合采样训练策略 → 参数回传 Actor。**数据质量决定策略上限**。

#### 3.1.3 ROS2 控制节点搭建

将松灵机械臂 SDK 封装为 ROS2 节点，提供底层控制能力：

1. 创建 ROS2 package，集成松灵臂官方 SDK。
2. 实现控制节点，订阅动作指令，发布关节状态 / 末端位姿。
3. 配置 MIT 混合控制模式（位置 + 力控混合）。

#### 3.1.4 Flask HTTP Bridge 搭建

在 ROS2 节点之上搭建 Flask HTTP 服务，向上层 RL 环境暴露 RESTful 接口：

| 接口 | 功能 |
|---|---|
| `getstate` | 获取当前观测（图像……） |
| `pose` | 获取 / 设置末端位姿 |
| `jointreset` | 重置机械臂到初始…… |
| `gripper_control` | 控制夹爪开合 |

**启动与验证要点：**

- Flask 服务运行在边缘控制 PC 上，作为 ROS2 控制层与上层 RL 算法层之间的通信桥梁。
- 启动后需验证接口连通性：用 `curl` 或简单脚本调用 `GET /getstate`，确认能返回图像和本体状态数据；调用 `POST /pose` 确认能控制机械臂运动。
- 接口响应延迟直接影响控制频率，需确保边缘 PC 与机器人之间通信稳定，避免网络抖动导致动作延迟。
- 训练过程中 Flask 服务需持续运行，一旦中断 Actor 将无法获取观测或下发动作，训练会卡住。

### 3.2 机器人配置

#### 3.2.1 机械臂连接与校准

1. 确认机械臂电源、急停按钮、通信线缆连接正常。
2. 启动 ROS2 控制节点，确认与机械臂通信正常。
3. 验证关节状态、末端执行器状态。

#### 3.2.2 控制模式

本项目采用松灵臂的 **MIT 混合控制模式**，支持位置控制与力控的混合，适用于插拔这类需要接触力反馈的精密任务。

#### 3.2.3 安全与初始化配置

- **姿态锁定**：USB 插拔任务中锁定末端姿态，仅保留平移自由度，降低动作空间维度。
- **初始化位置**：每次 episode 开始时，机械臂末端在一个 **5cm × 5cm** 的正方形区域内随机初始化，确保策略见过不同起始位置，提升泛化能力。
- **任务设定**：末端插头固定在夹爪上，训练过程中不学习夹爪开合动作，策略只需学习末端平移控制完成插接。

> 训练前需确认机械臂已回到安全初始位姿，工作空间内无障碍物。

### 3.3 相机与感知配置

#### 3.3.1 相机安装

- **腕部相机 ×2**：安装在末端执行器附近，提供第一视角（左右各一个）。
- **第三视角相机 ×1**：固定在工作空间侧方，提供全局视角，同时用于 reward classifier 图像采集。

#### 3.3.2 观测空间定义

策略的观测空间由以下部分组成：

- **视觉观测**：2 个腕部 RealSense 图像 + 1 个第三视角图像。
- **本体感知（proprio）**：机械臂关节角、关节速度、末端位姿等。

> 第三视角图像同时用于 reward classifier 的输入和策略观测。

### 3.4 动作空间定义

- **动作形式**：末端相对控制（relative action），输出归一化的末端平移增量（x, y, z 三维）。
- **为什么用相对量**：相对量较绝对量更容易学习，因为相对量的分布更加集中，策略不需要学习绝对坐标的偏移。
- **姿态约束**：结合任务约束锁定末端姿态，仅在平移维度上输出动作，降低动作空间维度。
- **夹爪固定**：末端插头固定在夹爪上，训练过程中不学习夹爪开合动作，夹爪始终保持夹持状态，策略只需输出末端平移控制。

### 3.5 Reward Classifier（二分类器）训练

对于 USB 插拔这类稀疏奖励任务，使用二分类 reward classifier 自动判断任务完成状态。以下是完整的训练流程、注意事项以及失效后的补救方法。

#### 3.5.1 训练流程总览

```text
┌────────────────────┐          ┌──────────────
│ 1. 数据采集        │ ───────► │ 2. 数据标……
│ （第三视角相机）   │          │ （成功/失败）
└────────────────────┘          └──────────────
……（后续步骤：3. 模型训练 → 4. 在线推理 → 5. 失效检测与再训练）
```

#### 3.5.2 数据采集

HIL SERL 官方提供了 `record_success_fail.py` 脚本用于采集二分类器训练数据，其核心机制是**默认失败、按键标记成功**：

```bash
# 进入 examples 目录，启动数据采集脚本
cd examples
python record_success_fail.py --exp……
```

**脚本工作原理：**

- 脚本启动后持续采集相机图像和 transition，所有帧默认标记为负样本（失败，label=0）。
- 当操作者按住空格键时，当前帧被标记为正样本（成功，label=1）。
- 脚本在收集到 `--successes_needed` 指定数量的正样本后自动终止（默认 200）。
- 数据自动保存到 `experiments/<exp_name>/classifier_data/` 目录。

**采集操作要点：**

- 用 SpaceMouse 遥操作机械臂执行任务，在任务明确成功的瞬间按住空格键标记成功帧。
- 其余时间（接近、接触、偏斜、半插入、脱落等）均自动记录为失败帧。
- 官方建议收集 **2~3 倍于正样本的负样本**，覆盖所有失败模式（如错误位置插入、半插入、插头悬空等）。
- 实际正负样本比例维持在约 **1:7**（正:负），符合训练中失败居多的真实分布。

> TIP：为训练出抗假阳性的分类器，应刻意在各种"看起来接近成功但实际失败"的状态下多停留采集负样本，例如插头偏斜接触、半插入、插错位置等。

#### 3.5.3 数据标注

- **正样本（标签=1）**：任务明确成功的帧（USB 完全插入插座）。
- **负样本（标签=0）**：任务失败或未完成的帧（未接触、接触但未插入、偏斜、脱落等）。
- **标注原则**：对于模糊帧（如半插入状态），根据任务实际判定标准统一标注，避免标注不一致导致训练噪声。

#### 3.5.4 模型训练

训练命令：

```bash
# 进入任务实验目录，启动二分类器训练
cd experiments/<任务名称>
python ../../train_reward_classifi……
```

- 训练数据自动从 `experiments/<exp_name>/classifier_data/` 读取（即 `record_success_fail.py` 采集的数据）。
- 训练完成的模型 checkpoint 保存到 `experiments/<exp_name>/classifier_ckpt/` 目录。
- 训练使用配置文件中 `classifier_keys` 指定的相机图像作为输入。

**模型架构：**

- **Backbone**：预训练的 **ResNet10**（从 SERL 官方 releases 下载预训练权重），提取图像特征。
- **分类头**：`Linear → Dropout → LayerNorm → ReLU → Linear(1)`，最终输出单个 logit，经 sigmoid 激活得到成功概率。
- 训练时 backbone 可冻结底层、微调高层，或全网络使用较小学习率微调。

**分类损失函数**：Binary Cross Entropy（BCE Loss）——二分类器使用二元交叉熵损失，本质是让模型学会区分"成功视觉特征"和"失败视觉特征"。

**类别不平衡处理：**

由于正负样本比例约 1:7（负样本远多于正样本），可使用以下方法缓解：

- **加权 BCE Loss**：给正样本赋予更高的损失权重（如权重 7:1），平衡梯度贡献。
- **Focal Loss**：降低易分类样本的权重，聚焦难分类样本，适合存在大量简单失败帧的场景。

**评估指标**：在独立测试集上评估，目标准确率达到 **90% 以上**；同时关注精确率（precision）和召回率（recall），避免假阳性（误判成功）过多——假阳性会导致策略在未完成任务时获得奖励，严重影响训练效果。

#### 3.5.5 在线推理

- 训练过程中持续采集第三视角图像送入 classifier。
- 当 classifier 对当前状态的判别置信度（sigmoid 输出）达到 **0.8 以上**时，判定任务成功，给予奖励。
- 建议采用**连续多帧判定**（如连续 3~5 帧均超过阈值），避免单帧误判导致奖励噪声。

#### 3.5.6 失效检测与针对性再训练（重点）

二分类器在实际部署中可能出现误判，需要建立"**检测 → 针对性采集 → 再训练**"的闭环：

**第一步：失效检测**

- **假阳性（误判成功）**：实际任务失败，但 classifier 输出高置信度成功。常见于插头偏斜但视觉上接近成功、半插入状态、光照变化导致外观相似等。
- **假阴性（漏判成功）**：实际任务成功，但 classifier 未识别。常见于成功姿态与训练样本差异较大、遮挡、反光等。

**检测方法：**

- 人工抽查训练日志中的 reward 触发帧，确认是否与实际结果一致。
- 在评估 rollout 中对比 classifier 判定与人工标注的差异。
- 记录低置信度（0.4~0.6 区间）的模糊帧，这些是 classifier 最不确定的区域。

**第二步：针对性数据采集**

针对检测到的误判类型，定向采集困难样本：

| 误判类型 | 针对性采集策略 |
|---|---|
| 假阳性（偏斜误判为成功） | 在插头偏斜、接触但…… |
| 假阴性（成功未识别） | 在新的成功姿态、不…… |
| 模糊边界（半插入） | 专门采集半插入、临…… |
| 光照 / 背景变化 | 在不同时间段、不同…… |

- 采集时重点覆盖 classifier 置信度在 **0.4~0.6 之间**的模糊区域，这些是模型最需要补充学习的样本。
- 新采集的难例数据应与原始训练数据合并，保持合理的正负样本比例。

**第三步：在预训练模型基础上再训练**

- **不要从头训练**：基于已有的预训练 ResNet 权重（或上一版 classifier checkpoint）继续微调，利用已学到的通用视觉特征。
- **微调策略**：
  - 使用较小的学习率（如原始学习率的 1/10），避免灾难性遗忘。
  - 可以冻结 backbone 底层，仅微调高层和分类头；或全网络使用低学习率微调。
  - 将新采集的难例数据与原始数据混合训练，必要时对难例样本赋予更高采样权重。
- **迭代循环**：再训练 → 部署 → 检测新误判 → 再采集 → 再训练，直到误判率降到可接受范围。

#### 3.5.7 注意事项

1. **第三视角相机位置固定**：训练和推理时相机位置、角度、焦距必须一致，否则会出现域偏移导致误判。
2. **光照一致性**：训练数据采集时的光照条件应与实际训练时一致，必要时使用固定光源。
3. **避免数据泄漏**：确保训练集和测试集来自不同的采集回合（episode），不要同一 episode 的帧同时出现在训练和测试中。
4. **定期更新**：随着任务环境变化（更换插座、调整夹具位置等），应重新评估 classifier 并按需补充数据。
5. **置信度阈值可调**：0.8 不是固定值，可根据假阳性 / 假阴性的代价调整——假阳性代价高则提高阈值，假阴性代价高则降低阈值。

### 3.6 RL 算法配置：RLPD

本项目使用 **RLPD（Offline-to-Online）** 算法，在 SAC 基础上改进，适合在线交互繁琐的机器人任务：

#### 3.6.1 RLPD 核心设计

1. **平衡采样 Prior Data 和 Online Data**：训练 batch 中混合已有专家数据 / 历史数据和在线交互数据，让策略既利用已有数据，又能通过在线交互继续改进。
2. **Ensemble Critic**：使用多个 Critic 集成，缓解 Q 值过估计，支持更高的数据复用率（高 UTD）。
3. **Critic 中使用 LayerNorm**：提高高 UTD 更新下的训练稳定性，减少 Q 网络发散。

**框架说明：**

- **Offline Buffer**：存储专家演示数据或历史采集数据，训练过程中基本固定，提供先验知识。
- **Online Buffer**：存储真机实时交互采集的 transition（含人工干预数据），持续增长更新。
- **混合采样**：每个训练 batch 从两个 Buffer 中按预设比例采样，让策略同时利用先验数据和在线探索。
- **Ensemble Critic**：多个 Q 网络集成，取最小值或均值，缓解单网络 Q 值过估计问题，支持高 UTD（Update-To-Data ratio）。
- **LayerNorm**：在 Critic 网络中使用层归一化，提高高更新频率下的训练稳定性。
- **参数广播**：Learner 更新后定期将 Actor 新权重同步到真机执行端，形成异步训练闭环。

#### 3.6.3 SAC 基础（RLPD 的底层框架）

- **Actor**：学习策略，最大化期望累计回报 + 熵正则（鼓励探索）。
- **Critic**：学习 soft Q 值，通过 TD target 构造均方误差 loss。
- 连续动作空间中，Actor 输出高斯分布的均值和标准差，采样得到动作。

### 3.7 人工干预与遥操作

训练过程中，操作者通过 **SpaceMouse** 随时介入：

| 设备 | 操作 |
|---|---|
| SpaceMouse | 六维自由度输入 |
| 键盘 | 特定按键 |

**干预机制：**

- 当策略即将失败或机械臂进入不期望区域时，操作者通过 SpaceMouse 接管控制。
- 干预数据会回流到 **Replay Buffer** 中，参与后续策略更新，加速收敛。
- 这是 HIL（Human-In-the-Loop）的核心：**人类不仅是安全网，也是数据来源**。

#### 3.7.1 训练阶段干预时间线

实际训练过程中，人工干预按以下节奏进行，策略随干预持续逐步收敛：

| 阶段 | 时间 | 操作 |
|---|---|---|
| 初始数据采集 | 训练前 | 用 SpaceMouse 采集 20 条演示数据，作为 Offline Buffer 的 prior data |
| 早期干预 | 训练开始后 ~1 小时 | 持续通过 SpaceMouse 干预动作和无效探索，干预数据…… |
| 中期干预 | 1~3 小时 | 随着策略改善，干预频率逐……策略失败或进入危险区域时…… |
| 收敛阶段 | 约 3 小时 | 干预极少，策略自主完成任…… |

**关键要点：**

- **初始 20 条**专家数据是训练的起点，质量直接影响早期收敛速度。
- **前 1 小时**是干预最密集的阶段，需要操作者持续关注并及时修正。
- 干预数据与在线探索数据共同构成训练样本，人类演示的质量和数量决定了策略上限。
- 总训练时长约 **3 小时**可达到 100% 成功率（具体时间因任务难度和硬件而异）。

#### 3.7.2 源码实现：干预动作优先机制

HIL SERL 源码中通过 `SpacemouseIntervention`（`gym.ActionWrapper` 派生类）实现干预动作优先执行。核心逻辑是**硬替换（hard override）**——一旦检测到 SpaceMouse 输入，策略动作被完全丢弃，直接执行人类动作。

核心代码逻辑（`wrappers.py` 中的 `SpacemouseIntervention.action()`）：

```python
class SpacemouseIntervention(gym.A……):
    def action(self, action): np.nd……
        # 1. 实时读取 SpaceMouse 状态……
        expert_a, buttons = self.e……

        # 2. 干预检测：L2 范数超过死区……
        intervened = False
        if np.linalg.norm(expert_a ……):
            intervened = True

        # 3. 处理夹爪按键（左键关，右键……）
        if self.left:
            gripper_action = np.ra……
            intervened = True
        elif self.right:
            gripper_action = np.ra……
            intervened = True

        # 4. 硬替换：有干预则返回专家动……
        if intervened:
            return expert_a, True
        return action, False
```

**执行优先级**：人类指令 > 策略指令。每个控制步独立判断，没有过渡期或混合：

```text
Step 1: 人类移动 SpaceMouse → exper……
Step 2: 人类移动 SpaceMouse → exper……
Step 3: 人类松手 → norm=0 ≤ 0.001 →……
Step 4: policy_action, intervened=……
```

**干预数据的双通道存储**：干预 transition 同时写入两个 Replay Buffer，确保干预数据不会被海量在线探索数据稀释：

| Buffer | 名称 |
|---|---|
| 在线经验 Buffer | `replay_buffer`（actor_env……） |
| 干预经验 Buffer | `demo_buffer`（actor_env_int……） |

- **Actor 端**：`data_store.insert(transition)`（全部写入）+ `intvn_data_store.insert(transition)`（仅干预时写入）。
- **Learner 端**：RLPD 采样时从两个 Buffer 按比例混合，**干预数据权重保持 50%**，确保人类纠偏信号在训练中占主导地位。
- **Transition 中的 `actions` 字段始终是实际执行的动作**（通过 `actions = info.pop("intervene_action")` 替换），Learner 直接学习人类动作，无需额外标签。

**死区阈值说明**：0.001 看似极低，但 SpaceMouse 静止时输出接近 0，实际操作的 L2 范数通常在 0.01~1.0 量级，远超阈值。该阈值本质上只过滤 HID 硬件噪声，不区分"轻微触碰"和"有意操作"。

### 3.8 训练启动

训练采用 **分布式 Actor-Learner 架构**，需同时启动两个进程：Actor 端负责与机器人交互、采集数据、执行人工干预；Learner 端负责从 Replay Buffer 采样、更新策略网络、定期将新权重同步给 Actor。两者通过网络通信，启动顺序无严格要求，但需确认连通后再让机器人开始运动。

#### 步骤 1：启动 Actor 端（机器人侧）

Actor 端运行在边缘控制 PC 上，需依次启动以下组件：

1. **ROS2 控制节点**：封装机械臂 SDK，提供底层控制和状态发布。
2. **Flask HTTP Bridge**：在 ROS2 之上暴露 RESTful 接口，供 Actor 进程调用。
3. **Actor 进程**：加载策略网络，通过 Flask 接口获取观测、下发动作，同时监听 SpaceMouse 输入执行人工干预，采集的 transition 通过 ZMQ 上传到 Learner 端。

**注意事项：**

- 启动后先用 `curl` 验证 Flask 接口连通，确认 `GET /getstate` 能返回图像和本体状态。
- 确认 SpaceMouse 已被系统识别，干预通道可用（手不离开 SpaceMouse，随时准备接管）。
- 确认机械臂已回到安全初始位姿，工作空间内无障碍物。
- Actor 进程启动初期策略是随机的，机械臂动作可能剧烈，必须限速、限工作空间。

#### 步骤 2：启动 Learner 端（GPU 侧）

Learner 端运行在本地 RTX 4090 主机上，负责策略训练：

1. 加载配置文件（算法选择、超参数、Buffer 配置、Reward Classifier 路径等）。
2. 初始化 RLPD 算法（Actor、Ensemble Critic、双 Replay Buffer）。
3. 加载预训练的 Reward Classifier，用于在线推理生成奖励信号。
4. 从 Actor 端接收 transition 数据，混合采样训练，定期将新权重广播回 Actor。

**注意事项：**

- 确认 GPU 显存充足（RTX 4090 24GB 足够运行 RLPD + ResNet Classifier）。
- 确认 WandB 已配置，训练过程中可实时监控 reward、成功率、干预率等指标。
- Learner 与 Actor 之间的网络需稳定，数据上传和参数广播延迟过高会影响训练效率。

#### 步骤 3：确认训练启动

- 检查 WandB 是否有数据上报（reward、loss、buffer 大小等曲线开始变化）。
- 观察机器人是否开始探索动作（初期动作随机，需密切关注安全）。
- 检查 Replay Buffer 是否有数据写入（含 prior data + online data + 干预数据）。
- 确认 Reward Classifier 在线推理正常，成功帧能触发奖励。

#### 3.8.1 训练过程监控与判断标准

训练启动后，需要持续监控训练状态，判断策略是否在正常收敛，并及时发现异常。以下是核心监控指标、正常曲线预期、异常信号应对和停止训练的判断标准。

**一、核心监控指标（WandB 实时查看）**

| 指标 | 含义 |
|---|---|
| reward / episode | 每个 episode 的累计奖励 |
| success rate | 评估 rollout 的成功率 |
| intervention rate | 人工干预步数占比 |
| Q 值（Critic） | Critic 网络输出的状态价值 |
| actor loss / critic loss | 策略网络和价值网络的损失 |
| buffer size | Replay Buffer 中存储的 trans…… |
| reward trigger count | Classifier 触发成功奖励的次数 |

**二、正常训练曲线的分阶段预期**

参照本项目 USB 插拔任务的实际经验，训练过程大致分为三个阶段：

| 阶段 | 时间 | reward 表现 |
|---|---|---|
| 早期探索 | 0~1 小时 | reward 低且波动大，多数 episode 无成功奖励 |
| 中期收敛 | 1~2.5 小时 | reward 稳步上升，部分 episode 能获得成功奖励 |
| 后期稳定 | 2.5~3 小时 | reward 高位稳定，多数 episode 成功 |

> **判断要点**：如果训练 1 小时后 reward 仍然始终为 0、success rate 没有任何上升趋势，说明训练可能存在问题，需要暂停排查。

**三、异常信号与应对**

| 异常现象 | 可能原因 |
|---|---|
| reward 始终为 0 | Classifier 未触发成功奖励……机偏移；阈值设置过高 |
| Q 值剧烈飙升 / 发散 | 学习率过高；UTD（更新……大；Critic 不稳定 |
| 干预率不降反升 | 策略在学坏；动作空间定义……励信号有噪声 |
| 机械臂动作剧烈 / 撞桌 | 初始探索率过高；安全限位……作缩放过大 |
| actor loss / critic loss NaN | 学习率过高；梯度爆炸；……值 |
| buffer 不增长 | Actor 与 Learner 网络不通……中断；Actor 进程卡住 |
| success rate 到一定值后停滞 | 遇到性能瓶颈；数据多样性……Classifier 误判限制上限 |

**四、停止训练的判断标准**

当以下条件同时满足时，可以认为训练完成，停止训练并导出模型：

1. **成功率达标**：连续多次评估 rollout 的 success rate 稳定在目标值以上（如 95%+），不再有明显波动。
2. **干预率极低**：训练过程中人工干预率降到接近 0，策略能自主完成绝大多数 episode。
3. **reward 稳定**：reward 曲线在高位平稳，不再有明显上升趋势，说明策略已收敛。
4. **动作质量合格**：观察机器人执行任务的动作，平滑、稳定、无多余抖动，接触阶段无明显碰撞或打滑。
5. **鲁棒性验证**：在不同初始位置（5cm×5cm 随机范围内）多次测试，均能稳定成功，说明策略具备一定泛化能力。

> 注意：不要过早停止训练。如果 success rate 刚达到目标值但波动较大，建议继续训练 10~20 分钟确认稳定性后再停止。

## 4. 踩坑记录与常见问题

### 4.1 成功率仅 80% 的原因分析

- **现象**：USB 插拔任务最终成功率约 80%，未达到更高水平。
- **原因分析**：
  a. **二分类器误判**：部分实际成功的任务，reward classifier 未判定为成功，导致策略未得到正确奖励信号。
  b. **夹爪姿态偏移**：夹爪夹持插头接触时，会让插头位置姿态发生一定变化，导致插接失败。
- **改进方向**：
  - 在夹爪上加装**触觉传感器**，将触觉反馈融入策略观测，提升接触阶段的控制精度。
  - 针对 classifier 误判，采集更多边界 case 样本重新训练。

### 4.2 Reward Classifier 误判

- **现象**：错误状态被 classifier 误判为成功（假阳性），或成功状态未被识别（假阴性）。
- **解决方案**：采集特定位置 / 刁钻角度的错误数据集，重新训练 classifier，提升困难样本上的识别准确率。
- **预防措施**：训练时保持正负样本 1:7 的合理比例，定期用新采集的难例微调。

### 4.3 夹爪接触导致姿态变化

- **现象**：夹爪夹持插头与插座接触时，插头位置 / 姿态发生偏移，导致插接失败。
- **原因分析**：纯视觉策略缺乏接触力反馈，无法在接触瞬间做精细调整。
- **改进方向**：引入触觉传感器，或使用力控模式（MIT 混合控制中的力控维度）做接触阶段的柔顺控制。

## 5. 扩展方向与改进路线

在现有 HIL SERL 真机部署基础上，以下三个方向可以进一步提升策略性能、泛化能力和接触型任务的鲁棒性。每个方向均说明如何复用现有硬件，以及如何逐步借用这些改进。

### 5.1 RL-100：扩散策略 + 三阶段训练

**方向说明**

RL-100 是 2026 年发表于 Science Robotics 的真机强化学习框架，核心思想是在**扩散视觉运动策略（Diffusion Policy）**上做三阶段训练：

1. **模仿学习预训练**：用人类遥操作数据训练扩散策略，建立有能力的基线。
2. **迭代离线 RL**：用已采集数据做离线 RL，通过 Offline Policy Evaluation（OPE）门控 PPO 风格的更新，保证保守可靠的策略提升。
3. **在线 RL**：在真实环境中少量在线交互，消除残余失败模式。
4. **一致性蒸馏**：将多步扩散采样压缩为单步策略，推理延迟降低一个数量级，满足高频控制需求。
